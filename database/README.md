# Order booking database setup

1. Start Apache and MySQL in XAMPP.
2. Open phpMyAdmin, choose **Import**, and import `database/order-booking.sql`. It creates the database `order-booking` and separate `agents`, `distributors`, `transporters`, and `customerRecords` tables. This is the complete schema for a fresh database. All four tables include phone constraints and unique email indexes.
3. Connection settings are in `includes/db.php`: host `127.0.0.1`, port `3306`, database `order-booking`, username `root`, empty password. Change these defaults to match your MySQL setup, or set `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` in the server environment. PHP needs PDO MySQL and mbstring (included with XAMPP).
4. Open the application through Apache, then use the existing Agent, Distributor, and Transporter pages. Add, edit, delete, and list operations now use the database. Success appears only after the API accepts the change; database errors appear in the form instead.

## Automatic live schema updates

Hostinger Git deployment synchronizes files but does not execute SQL files. Versioned SQL files in `database/migrations/` are applied automatically the first time a PHP API connects to MySQL after deployment. Applied migration filenames are recorded in `appSchemaMigrations`; each migration runs once, in filename order. Migration statements use idempotent DDL/DML so they can be safely retried if a deployment is interrupted.

Configure `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` and `DB_PASSWORD` in Hostinger's PHP environment or in the server's `includes/db.php` connection settings. Do not put live credentials in Git. Back up the live database before deploying schema changes. The current migration adds the piece-item catalog and manufacturing-state tables without replacing existing application data. SQL and migration files are blocked from direct web access.

## Separate APIs

| Resource | Endpoint | Table |
| --- | --- | --- |
| Agent | `api/agent.php` | `agents` |
| Distributor | `api/distributor.php` | `distributors` |
| Transporter | `api/transporter.php` | `transporters` |
| Customer | `api/customer.php` | `customerRecords` |

Each endpoint supports `GET` (list), `POST` (create), `PUT` (update), and `DELETE` (delete). Writes require `Content-Type: application/json`. Create/update fields are `name`, `contact`, `email`, `city`, `state`; update/delete require `id`. IDs are generated by the API. Name, city, state and contact are required for all three types. Contact must be exactly 10 digits starting with 6, 7, 8 or 9. Email is optional, format-validated and unique within each table. Empty emails are stored as NULL.

Responses are JSON: `{ "success": true, "data": ... }` or `{ "success": false, "message": ... }`. Queries use prepared statements. Shared endpoint implementation is in `api/master-records.php`.

Existing browser-only records are not automatically uploaded or deleted. A compatibility cache of database records is maintained on these three pages for the existing customer/order dropdowns. Customer records also use the database; product and order persistence remains unchanged. Open the three master pages to refresh those cached dropdown lists on another browser.

SQL import and database integration have not been run against your MySQL instance; PHP and JavaScript syntax were checked.

Only `database/order-booking.sql` is required for a fresh installation. See `../flow.md` for the flow and table register; new table names use lower camelCase.

Customer create/update additionally accepts `shopName`, `agentId`, `transporterId`, `distributorId`. Name, shop name and phone are required. City/state/master selections remain optional for customers; supplied master IDs must exist. Re-import the single SQL file to add `customerRecords` to an existing database.

Manufacturing schema: `employeeRecords`, `colourRecords`, `additionalWork`, `itemList` are included in the same SQL file. These four table definitions follow the current forms; their pages now load/save/delete through api/employee.php, api/colour.php, api/item-list.php and api/additional-work.php. Hardcoded samples have been removed. Tables start empty. See `../flow.md` for fields and rules.

BOM Master and Product Creation now share `productRecords` via api/bom.php and api/product.php. `productItemLinks` and `productWorkLinks` enforce item/work foreign keys. Import the updated single SQL to add these tables. Uploaded images are stored in `uploads/products/`; PHP must be able to write to that directory. See flow.md for source flags, draft/completed/import behavior and validation.
