# Order booking database setup

1. Start Apache and MySQL in XAMPP.
2. Open phpMyAdmin, choose **Import**, and import `../database/order-booking.sql`. It creates the database `order-booking` and separate `agents`, `distributors`, `transporters`, and `customerRecords` tables. This is the complete schema for a fresh database. All four tables include phone constraints and unique email indexes.
3. **Connection file.** Copy `../includes/db.example.php` to `../includes/db.php`.
   - `db.php` is **not in Git**; every clone and server needs this copy.
   - When `db.example.php` changes in Git, copy it again.
4. **Connection settings.** Defaults: host `127.0.0.1`, port `3306`, database `order-booking`, username `root`, empty password. To use other values, either:
   - copy `../includes/db.config.example.php` to `../includes/db.config.php` and edit the copy; or
   - set `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` in the server environment. These take priority over the file.

   `db.php` and `db.config.php` are both ignored by Git. PHP needs PDO MySQL and mbstring (included with XAMPP).
5. **Order tables and accounts** (from the project folder, in a terminal or over SSH):
   - `php cli/orders-admin.php migrate` creates the order tables and the `appUsers` account table. It is safe to run again.
   - `php cli/users-admin.php create <username> admin "<Name>"` creates the first administrator. The password is typed on the next line (at least 8 characters).
   - Every page needs sign-in, so without an account nobody can use the application. Further accounts can be added on **Settings → Users**.
6. Open the application through Apache and sign in, then use the existing Agent, Distributor, and Transporter pages. Add, edit, delete, and list operations now use the database. Success appears only after the API accepts the change; database errors appear in the form instead.

## Automatic live schema updates

Hostinger Git deployment synchronizes files but does not execute SQL files. Versioned SQL files in `../database/migrations/` are applied automatically the first time a PHP API connects to MySQL after deployment. Applied migration filenames are recorded in `appSchemaMigrations`; each migration runs once, in filename order. Migration statements use idempotent DDL/DML so they can be safely retried if a deployment is interrupted. The custom BOM pattern migration adds `patternRecords` and `patternPieceLinks` without clearing any existing records.

Configure the live connection in one of two places, both of which survive deploys:
- Create `includes/db.config.php` on the server once, from `includes/db.config.example.php`, using the Hostinger File Manager. It is ignored by Git, so deploys never overwrite it. Keep the example's exact shape: `<?php`, then `return [ 'DB_HOST' => '…', … ];` and nothing else. Do not paste the old `db.php` into it, and do not write plain text. A malformed file is ignored and logged in the PHP error log ("includes/db.config.php ignored: …").
- Or set `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` and `DB_PASSWORD` in Hostinger's PHP environment.

**`includes/db.php` on the server.** It is not in Git, so deploys neither update nor delete it. After a deploy that changes `includes/db.example.php`, copy that file over `includes/db.php` in the File Manager.

**One-time switch-over,** for the deploy that removes `db.php` from Git. That deploy deletes `includes/db.php` on the server, so do these steps in order:
1. **Before merging:**
   - Download `includes/db.php` from the server to your PC as a backup. Don't leave a copy inside `public_html`.
   - Make sure `includes/db.config.php` exists with the live values, or that the `DB_*` variables are set.
2. Merge the pull request and let Hostinger deploy. The APIs fail from this moment.
3. **Immediately afterwards:** in the File Manager, copy `includes/db.example.php` to `includes/db.php`. The APIs work again.
4. Open a page that uses the database (for example, BOM Master) and check that it loads.

Do not put live credentials in Git. Back up the live database before deploying schema changes. The current migration adds the piece-item catalog and manufacturing-state tables without replacing existing application data. SQL and migration files are blocked from direct web access.

## Separate APIs

| Resource | Endpoint | Table |
| --- | --- | --- |
| Agent | `../api/agent.php` | `agents` |
| Distributor | `../api/distributor.php` | `distributors` |
| Transporter | `../api/transporter.php` | `transporters` |
| Customer | `../api/customer.php` | `customerRecords` |

Each endpoint supports `GET` (list), `POST` (create), `PUT` (update), and `DELETE` (delete). Writes require `Content-Type: application/json`. Create/update fields are `name`, `contact`, `email`, `city`, `state`; update/delete require `id`. IDs are generated by the API. Name, city, state and contact are required for all three types. Contact must be exactly 10 digits starting with 6, 7, 8 or 9. Email is optional, format-validated and unique within each table. Empty emails are stored as NULL.

Responses are JSON: `{ "success": true, "data": ... }` or `{ "success": false, "message": ... }`. Queries use prepared statements. Shared endpoint implementation is in `../api/master-records.php`.

Existing browser-only records are not automatically uploaded or deleted. A compatibility cache of database records is maintained on these three pages for the existing customer/order dropdowns. Customer records also use the database; product and order persistence remains unchanged. Open the three master pages to refresh those cached dropdown lists on another browser.

SQL import and database integration have not been run against your MySQL instance; PHP and JavaScript syntax were checked.

Only `../database/order-booking.sql` is required for a fresh installation. See `flow.md` for the flow and table register; new table names use lower camelCase.

Customer create/update additionally accepts `shopName`, `agentId`, `transporterId`, `distributorId`. Name, shop name and phone are required. City/state/master selections remain optional for customers; supplied master IDs must exist. Re-import the single SQL file to add `customerRecords` to an existing database.

Manufacturing schema: `employeeRecords`, `colourRecords`, `additionalWork`, `itemList` are included in the same SQL file. These four table definitions follow the current forms; their pages now load/save/delete through ../api/employee.php, ../api/colour.php, ../api/item-list.php and ../api/additional-work.php. Hardcoded samples have been removed. Tables start empty. See `flow.md` for fields and rules.

BOM Master and Product Creation now share `productRecords` via ../api/bom.php and ../api/product.php. `productItemLinks` and `productWorkLinks` enforce item/work foreign keys. Import the updated single SQL to add these tables. Uploaded images are stored in `../uploads/products/`; PHP must be able to write to that directory. See flow.md for source flags, draft/completed/import behavior and validation.
# Item configuration update (2026-10-26)

`itemList.itemType` is nullable and accepts `Cutting` or `Non-Cutting`. NULL is the explicit legacy/unconfigured state; existing rows are not auto-classified. The Item List API requires a valid type for new writes, returns it in list rows, and new BOM material selections must reference configured items. Apply `database/migrations/20261026_item-types-piece-photos.sql` to an existing installation; it is additive and safe to retry on MySQL/MariaDB versions supporting `ADD COLUMN IF NOT EXISTS`. Fresh installs include both columns in `database/order-booking.sql`.

`pieceItemList` is the existing separate garment-piece catalog used by BOM JSON (`pieceItemId`), so no duplicate piece master was added. `pieceItemList.photo` is reserved for secure piece imagery; uploading/editing those images is not yet exposed in the master UI/API.
